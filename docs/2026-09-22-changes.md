## 总账

单次点击（mousedown）的端到端耗时：

```text
约 530ms  基线
    ↓  业务侧 onDragStart / onDrag 补 useCallback
  246ms
    ↓  业务侧 sidebar.jsx 的 state.nodes 订阅按 tab 门控
  216ms
    ↓  业务侧 ConfigProvider 的 getPopupContainer 改用模块级函数
   97ms  当前
```

- **降幅约 82%，三刀全在业务侧**，共同点都是**引用不稳定导致 Context 广播或大面积重渲染**
- **craft 侧的订阅层优化（3 轮）端到端收益全是 0**，因为 collect 只占单次 mousedown 的约 2%
- craft 侧唯一有端到端收益的是 `onNodesChange` 的回归修复：消掉了 hover 和点击后每次约 45ms 的卡顿

拖拽稳态（2026-09-23，和点击分开统计）：

```text
临时 A/B：仍由 translate3d 产生的约 1589 个目标层
Layerize 约 83ms  ->  7.23ms（约 -91%）

完整修复后手工录制：
Layerize 常态 <= 10ms；单个代表帧 5.01ms
mousemove 的强制 Layout 3.75–3.91ms
```

- 拖动过程已没有明显卡顿感；这解决的是**持续拖动帧**，不是首次按下。
- 首次 `mousedown` 仍有一次性初始化：两次录制分别看到 `Event: mousedown 66.33ms`、`Task long task 74.99ms`；它不随每个移动帧重复。

## 一、craft 侧（`E:\source-code\craft.js`）

改动全部在工作区未提交，已构建并打进业务仓库的 `patches/@craftjs__core@0.2.12.patch`。

### 1. 临时测量设施（已移除）

- **用途**：本轮排查期间曾在 `Watcher.notify` 周围记录 dispatch、collect、结果变化和到下一帧耗时，并用于路径订阅 A/B 对比。
- **提交前清理**：运行时测量模块、全局测量对象、A/B 开关和对应测试均已删除，不再进入发布包。
- **说明**：本文及交接文档中的测量数字是历史证据；后续若继续优化，需重新建立一次临时测量并在验证后删除。

### 2. 订阅按 patch path 建索引 + no-op dispatch 防护

- **文件**：`packages/utils/src/useMethods.ts`（+249 行）、`packages/utils/src/tests/useMethods.test.tsx`（新增）
- **改动**：`Watcher` 用前缀树索引订阅者，`notify(patches)` 只唤醒与变更路径相交的订阅者；未声明 `dependencies` 的订阅仍走全局通道；`dispatch` 在 `newState === previousState` 时不再 `notify`
- **收益**：**端到端 0**。被唤醒的订阅者数确实下降，但 collect 只占单次 mousedown 的约 2%
- **保留原因**：逻辑更干净、无害，且为 `useNode` 的节点级订阅提供了基础设施

### 3. `useCollector` 的 `initialCollected`

- **文件**：`packages/utils/src/useCollector.tsx`
- **改动**：把首次 render 已经收集到的值作为 `Subscriber.collected` 的初始基准。此前基准是 `undefined`，首次 notify 时 `isEqualWith(recollect, undefined)` 永不相等，**每个订阅在挂载后都白白浪费一次 React 重渲染**
- **收益**：一次点击的结果变化数 **959 → 67（−93%）**、collect 耗时 **84.1 → 32.7ms（−61%）**，但**端到端 583.4 → 583.8ms，纹丝不动**
- **价值**：这是 upstream craft.js 同样存在的真实缺陷，值得回馈社区；但它不是本项目的卡点

### 4. `useNode` 的节点级订阅

- **文件**：`packages/core/src/nodes/useInternalNode.ts`
- **改动**：自动登记 `dependencies: [['nodes', id]]`，其他节点的数据变化不再执行本节点的 collector
- **收益**：**端到端 0**（同第 2 条）

### 5. `onRender` 不再是全局订阅

- **文件**：`packages/core/src/render/RenderNode.tsx`、`packages/core/src/render/tests/RenderNode.test.tsx`
- **改动**：`onRender` 订阅声明 `dependencies: [['options','onRender']]`，依赖常量提到模块作用域避免每次 render 重建订阅
- **收益**：**端到端 0**。干掉了 N 个全局订阅（N = 渲染中的节点数），但同样受 2% 的天花板限制

### 6. `setNodeEvent` 集合去重 + `setDOM` 支持批量

- **文件**：`packages/core/src/editor/actions.ts`、`packages/core/src/editor/tests/actions.test.ts`
- **改动**：
  - `setNodeEvent` 先把 selector 解析成有效 Node id 集合，与当前集合比较数量和成员，**相同则直接返回**（忽略数组顺序），不再清空重建 Set
  - `setDOM` 接受 `[id, dom][]` 批量，向后兼容原签名；批量里的未知 id 被忽略而不抛错
- **收益**：重复 hover、重复选中、重复清空不再产生 dispatch。**hover 抖动不是 mousedown 的卡点**（A/B 实测：移入即点 vs 停留 2 秒再点，dispatch 数都是 2），所以这条没有端到端收益，属于「消除确定性浪费」

### 7. `connect` 的 `setDOM` 攒批 + 拖拽 rAF 收敛

- **文件**：`packages/core/src/events/DefaultEventHandlers.ts`
- **改动**：
  - `connect()` 把 DOM 注册攒进**实例级**队列（不能放 `handlers()` 闭包里，否则每个 hook 一个队列、批量失效），`queueMicrotask` 里合并成一次 `setDOM` dispatch
  - 拖拽相关的 rAF 收敛成一个调度器
- **收益**：挂载 N 个节点从 **N 次 dispatch → 1 次**；rAF 从 **97 个/帧 → 1 个**。影响首屏和大量节点挂载，**不影响 mousedown**
- **风险与结论**：`node.dom` 在 `connect()` 返回后的同一同步块内还是空的。所有 `node.dom` 的消费方（`Positioner.getDOMInfo`、`RenderEditorIndicator`）都在事件回调里，跨了 microtask，因此安全

### 8. `useEditor` 的 `actions` 引用稳定化

- **文件**：`packages/core/src/hooks/useEditor.tsx`、`packages/core/src/hooks/tests/useEditor.test.tsx`
- **改动**：`getPublicActions(internalActions)` 原本在渲染期无条件执行、每次返回新对象，又被当作 `useMemo` 的依赖，**memo 永不命中**。改为把计算移进 `useMemo`，依赖换成引用稳定的 `internalActions`
- **收益**：未单独量化。每个 `useEditor` 调用点、每次渲染都会重建 `actions`，新引用还会让下游所有以 `actions` 为依赖的 `useCallback` / `useMemo` / `useEffect` 连锁失效——在有几千个调用点的项目里是确定性浪费
- **附带结论**：业务侧 `useStableEditor` 的 getter 代理**不是多余保险**，它一直在兜这个缺陷；它注释里「craft 内部本来就是稳定引用」的说法是错的

### 9. `onNodesChange` 只在节点数据变化时回调 ⭐ 本轮唯一有端到端收益的 craft 改动

- **文件**：`packages/core/src/editor/Editor.tsx`、`packages/core/src/editor/tests/Editor.test.tsx`（新增，13 例）
- **背景（这是我们自己引入的回归）**：
  - **原版 craft**：collector 是 `query.serialize()`，结果相等就不回调，语义是「只有数据真的变了才回调」。代价是每次 dispatch 都同步序列化整棵树
  - **中间一版补丁**：collector 换成自增计数器，同步序列化确实省掉了，但计数器每次都变，**语义退化成「每次 dispatch 都回调」**。于是 hover 和选中也会进业务侧的 debounce，300ms 后白跑一次 5000 节点的全量序列化——LoAF 实测**每次约 45ms**。开销只是从同步挪到了异步，并没有消除
- **改动**：collector 改为按引用比较**节点集合、每个 `node.data`、`options.resolver`** 三者，只有它们之一变化时才递增版本号
  - 正确性依据：`serialize()` 只读这三样（`NodeHelpers.toSerializedNode` → `serializeNode`），且 craft 内所有 `.data.x =` 要么在 Immer draft 里、要么是给还没入库的新节点赋值，**不存在绕过 Immer 原地修改 `data` 的情况**，所以引用比较不会漏报
  - 开销：hover 这类操作做 O(n) 次引用比较（5000 节点约 0.1ms）；`nodes` 引用没变的操作（`setIndicator`、`setOptions`）直接跳过
- **收益**：**hover 时每帧约 45ms 的 `timerExpired` 消失；点击之后的那次也消失；修改属性时照常回调一次**（实测已验证三种场景）
- **单测**：hover、选中、`setDOM`、不改 resolver 的 `setOptions` **不**回调；`setProp`、`setHidden`、增删节点、撤销重做、更换 resolver **会**回调；订阅后首次变化必定回调

## 二、业务侧（`E:\code\deeplogic.designer`）

### 1. `onDragStart` / `onDrag` 补 `useCallback` ⭐

- **文件**：`useCanvas.tsx:306, 371`
- **背景**：`contextValue` 有 32 个依赖，逐项埋点比对后发现只有这两项每次都换引用——因为它们**根本没被 `useCallback` 包裹**，其中 `onDrag` 还是个**什么都不做的空函数**。一个空函数每次换引用，就把整个 Context 广播给了几百个组件
- **收益**：`contextValue` 换引用 **10/10 → 0**；mousedown **483–526ms → 322–408ms（约 −35%，省约 170ms）**
- **回归**：改的是拖拽起点计算，回归清单见 `perf-handoff.md` §9.2（**尚未回归**）

### 2. 图层面板不再无条件订阅整个 `state.nodes` ⭐

- **文件**：`sidebar.jsx:487`
- **背景**：`useStableEditorSelector((state) => state.nodes)` 每次 dispatch 必中——hover 和选中都会改 `node.events`，Immer 随之换掉 `state.nodes` 的引用。ctx-watch 实测**每次 dispatch（包括 hover）都会把整个 Sidebar 重渲染一遍**。而这份全量 nodes **只有图层 tab 用得到**
- **改动**：用 `activeRef` 读当前 tab，非图层 tab 时 collector 返回 `null`；结果包一层 `{ layerNodes }`，避免 `useEditor` 把数千个节点展开进返回对象（原先每次渲染都是新引用，下游 `useMemo` 永不命中）；刚切到图层 tab 时用 `query.getState().nodes` 兜底，保证首帧不为空
- **收益**：**hover 不再重渲染 Sidebar**；单次点击帧 **246ms → 216ms**；mousedown 回调没变
- **回归**：见 `perf-handoff.md` §9.2（**尚未回归**）

### 3. 画布外层 `ConfigProvider` 的 `getPopupContainer` 改用模块级函数 ⭐ 收益最大

- **文件**：`hooks/useGlobalTheme.tsx:183`
- **背景**：`<ConfigProvider getPopupContainer={() => ...}>` 传的是内联函数，每次渲染换引用。antd 的 ConfigContext 由 `useMemo` 计算、依赖里有它，于是**整个画布的 antd 消费者（Typography、Select 等）被 Context 穿透 `memo` 强制重渲染**，连带表单校验文案的 context 也被重算。同一个文件第 34 行早就有一个逻辑完全相同的模块级 `getThemeModalContainer`
- **改动**：一行——`getPopupContainer={getThemeModalContainer}`
- **收益**：**mousedown 回调 163ms → 61ms（−63%）**；单次点击帧 **216ms → 97ms（−55%）**
- **性价比**：本轮改动量最小、收益最大的一刀

### 4. 「已修改」基准的补记保障（正确性，不是性能）

- **文件**：`helper/utils.js`、`designer-view.jsx`、`hooks/useVersionPreview.ts`
- **背景**：业务里有 6 处约定「先把基准置为 `null`，由下一次 `onNodesChange` 重新记基准」。过去这其实是**靠随便一次 hover 碰巧兜住**的。craft 侧改成「只有数据变化才回调」之后，`useVersionPreview.ts` 的 `restoreDirtyState` 有一条路径（snapshot 无 content、跳过 `deserialize`）会让基准一直悬空，**用户的第一次真实编辑会被误记成基准 → 漏报「已修改」，切页不提示保存，改动可能丢失**
- **改动**：新增 `requestDesignerBaselineCapture()`（由 `designer-view.jsx` 注册，内部用已保存的 query 调用那个防抖过的 `onNodesChange`），在 `restoreDirtyState` 置 null 之后显式调用
- **刻意没有做的事**：没有把它塞进 `setDesignerBaseline(null)` 里全局生效。`designer-view.jsx` 退出模板预览时会在回调**内部**置 null，那时真实内容还没灌入，提前补记会把旧模板内容记成基准
- **收益**：无性能收益，是配合 craft 侧改动的正确性保障
- **回归**：7 条「已修改」相关回归点，见 `perf-handoff.md` §9.2（**尚未回归**）

### 5. `useComponent` 两个全局订阅合并为一个

- **文件**：`useComponent.tsx`（新增 `getComponentEditorSnapshot`）
- **收益**：订阅数 **9605 → 6857**、collect **−29%**，**端到端 0**
- **保留原因**：无害。它也是「collect 不是瓶颈」的一次独立验证

### 6. `positionStyle` 按签名缓存引用

- **文件**：`DesignerCanvas.tsx:578`（`getCachedPositionStyle`）
- **收益**：**端到端 0**
- **保留原因**：让 `memo` 真正生效，无害

### 7. 移除全部常驻 `will-change`

- **文件**：`transform.ts:51`、`nodesBox.tsx:30`、7 处管道/母版、2 处 less
- **收益**：`will-change` 元素 **1382 → 17**，层数 1805 → **1822（反而略增）**，**端到端 0**

## 三、口径说明

- **「端到端」= LoAF 的帧耗时或双 rAF 的「到下一帧」**（含 style/layout/paint/composite）。`collect` 耗时只是 collector 函数体的执行时间，**优化它对端到端无效**，这是本轮最贵的一课
- **Chrome Performance 的 Summary / Bottom-up 是选定区间的累计值**。必须在时间轴上拖选出**单次交互区间**再看，否则会被放大数倍——本轮据此错判过两次（`Layerize 539.8ms`、`Rendering 34.5%`），各浪费一轮优化
- **单次 mousedown 的真实分布**：Scripting 483ms（91%）、System 36ms（7%）、Rendering 11ms（2%）。**瓶颈 100% 在 JS**
- 录制 Performance 时**必须关掉 React DevTools Profiler**，否则 `Profiling overhead` 会占到 28.8%
- React DevTools 的「Why did this render?」在本项目里一律显示 *first time rendered*，**不可信**（埋点实测 mount 0 / unmount 0）。判断「谁在换引用」要用 ctx-watch 脚本（`perf-handoff.md` §9.1）

6. **新发现，待定位层扩散原因**：监控画布进入可点击测点文本时，基础物料的 `:hover { transform: scale(1.1) }` 会触发临时合成提升，Layers 面板瞬时从正常状态跳至 **200+ 层**。已定位到共享入口，而非系统模板：`base/general/state.text/_style.js`、`base/general/numeral.text/_style.js`、`base/general/typography.text/_style.js`、`base/display/number.display/styles.module.less`。前两者已通过 `isMonitorCanvasNode` 区分监控画布，但当前只禁用常驻 `will-change`，仍保留 `scale(1.1)` 和 0.2s transition；文本标签和 `number.display` 同样存在缩放入口。**产品约束：监控测点的 `scale(1.1)` 及其动画效果必须保留。** 因此不能用“监控画布禁用缩放”规避问题，也不能重新加常驻 `will-change`。下一步应选中发生缩放的实际元素，确认 200+ 层是该元素自身的临时栅格化，还是父级/兄弟层被连带重建；只有后者才有不改视觉效果的收敛空间（缩小 transform 目标或隔离受影响绘制子树）。
   - **候选 A，优先实验**：只对当前 hover 的一个元素临时加 `will-change: transform`，在下一帧启动既有 `scale(1.1)` 过渡，`transitionend` 后清除。它保留同样的缩放和动画，但把层创建从动画首帧前移一帧；不能恢复常驻 `will-change`，且需用 Layers 和单帧 `Layerize` 做 A/B，确认没有把 200+ 层问题换成长期层。
   - **候选 B，前提是实际 DOM 证实范围过大**：把带背景色、边框、角标和文本组成一个紧凑的“视觉壳”，只缩放该壳，不缩放 Craft 的 `.target` / NodeBox 外壳。视觉边界不变，目标是阻断缩放向画布节点壳扩散；`state.text` / `numeral.text` 当前已缩放内层数值组，`number.display` 和 `typography.text` 要按实际元素边界判断。
   - **不采用**：以 `font-size` / `zoom` 替代 `scale`（会触发布局，且效果不等价）；`contain: paint` 直接包住缩放元素（可能裁掉放大后的边缘）；常驻 `will-change`（已证明会制造大量长期层）。
   - **预研结论（2026-09-23）**：**暂不实施。** 截图与手工交互确认，即使拖拽中移入这类文本节点也没有明显卡顿；当前缩放对象已是内层数值/单位组合或文本标签，并非 Craft `.target` 外壳。动态预热需要新增 pointer 事件、rAF、`transitionend` 清理，并同时覆盖编辑态与运行态的四套共享物料路径，可能重新引入 hover 事件开销或层回收问题。未观察到对应的长帧或交互损失前，200+ 的瞬时 Layers 数只是浏览器合成状态，不足以证明值得承担该回归风险。只有将来录到 hover 单帧 `Layerize` / LoAF 超过帧预算，才重开候选 A 的单点 A/B。
